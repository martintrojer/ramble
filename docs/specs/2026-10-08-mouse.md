# Mouse support

Status: approved design (user answers Q1–Q6). This reverses R3 in
`2026-10-07-ramble.md`, which parked mouse capture to keep tmux wheel
scrolling and drag-to-copy.

## Why R3 changes now

R3 kept the terminal's own mouse handling because ramble had no way to copy
text. Visual mode and the yank operator (t22) now exist, and drag-to-copy
(D4) brings back the terminal habit. Most terminals and tmux still give a
native selection with Shift+drag while an app captures the mouse. The
README says so, and one setting turns capture off.

## Decisions

### D1. Config and terminal setup

- `[mouse] enabled = true` (default). `false` leaves the mouse to the
  terminal or tmux, as before.
- When enabled, `run` sends `EnableMouseCapture` after
  `EnterAlternateScreen` and `DisableMouseCapture` before leaving. It also
  does this around every `suspend_and_run` (`src/app/run.rs:114`), so
  launched programs (the editor, tuicr) get a normal terminal, and on
  panic or exit through the existing restore path.
- `Event::Mouse` in `run.rs:86` becomes `AppEvent::Mouse(MouseEvent)`, and
  `App::event` passes it to `App::mouse(ev)`.

### D2. Hit-testing

The layout is decided in `ui::draw` (`src/ui/mod.rs`): the sidebar and its
panes (split by `split_ratio`), the review gutter, the text area, the
status line, and the popups (picker, help, hover, clue). Mouse handling
uses the same rectangles.

- `ui::draw` records a `Layout` in `App` (`App::set_layout`, through a
  `Cell` or by returning it from draw so `run` stores it). It holds
  `Rect`s for: the sidebar files pane, the outline pane, the text area,
  the gutter, the status line, the picker list, the help body, the hover
  box and the clue box (each optional).
- `App::hit(col, row) -> Hit` tests the popups first, in their draw order
  (top-most first), then the panes:
  - `Hit::Text { row, col }`: the rendered row and display column, after
    adding `scroll`.
  - `Hit::Files(index)` and `Hit::Outline(index)`: the item index, after
    the list's own scroll offset (`draw_list` works it out from the
    selection). The offset is recorded in the layout too, so a click
    lands on the drawn row. The title row is `None`.
  - `Hit::PickerItem(i)`, `Hit::Help`, `Hit::Hover`, `Hit::Clue`,
    `Hit::Status`, `Hit::Gutter`, `Hit::Border`, `Hit::None`.
- A `Layout::default()` (nothing drawn yet) makes every hit `None`, so
  tests that never draw get no mouse effect unless they set a layout.

### D3. Single click (left button, press)

| Where | Effect |
|---|---|
| Text | Focus content. Put the cursor on the clicked cell: on the row, at the column's grapheme, clamped to the line end, as for `$`. Leaves visual mode if active (as Esc). Not a jump: `C-o` history is unchanged. |
| Files row | Focus files and select the row. |
| The `▸`/`▾` cell of a folder row | Also expand or collapse it. |
| Outline row | Focus outline and select the row. |
| Picker item | Select it. |
| Outside an open picker, help or hover popup | Close it. The click does nothing else. |
| Status, clue, gutter, border | Nothing. |

The arrow cell is the two columns `▸ ` at the row's indent, recorded per
row in the layout or recomputed from the tree depth (and from the indent
cap, once `sb_width` lands).

### D4. Drag (left button held, in text)

- If the press was in text, the first `Drag` event starts a charwise
  visual selection from the press cell (`Mode::Visual(Char)` with the
  anchor at the press cell). Each later drag moves the cursor to the
  pointer cell, with the same clamping as a click.
- Dragging above or below the text area scrolls by 1 row per drag event,
  so the selection can extend past the screen.
- On release, if a selection was made by dragging, it is yanked exactly
  as visual `y` does (same source-text mapping, same status message,
  same clipboard), and visual mode stays active, so the selection stays
  visible. Press `y` again or Esc as usual. If you release without
  moving, no selection and nothing is copied.
- Drags that start in the sidebar or a popup are ignored.

### D5. Double and triple click

ramble detects these itself, because crossterm reports only presses. A
press is a double click when it falls on the same cell as the previous
press, within 400 ms, with the same button. A third such press is a
triple click. The counter resets after 400 ms or on a different cell.
Timing uses the `Instant` that `App::event` is given (tests inject it),
not wall-clock reads inside handlers.

| Where | Double | Triple |
|---|---|---|
| Text, on a link | follow it (`gd`) | — |
| Text, elsewhere | select the word (visual charwise over the vim `iw` word at the cell) and yank it, as on drag release | select the line (`V`) and yank it |
| Files row | open the file, or toggle the folder (as `Enter`) | — |
| Outline row | jump to the heading (as `Enter`) | — |
| Picker item | open it (as `Enter`) | — |

"Link" means the same link `gd` would follow at that cursor (the cursor
is first placed by the single-click handling of the first press).

### D6. Wheel

- The wheel scrolls the pane under the pointer and doesn't move focus.
- Text: 3 rows per notch, scrolling the view like `C-e`/`C-y`, keeping
  the cursor on screen.
- Files and outline: the selection moves 3 rows per notch (the lists
  scroll with the selection).
- Picker: the selection moves 1 row per notch.
- Help: scroll 3 rows.
- Hover: nothing.
- Horizontal wheel events are ignored.

### D7. Ignored

- Right and middle buttons.
- Clicks on the status line or the clue box.
- Dragging the sidebar border (it conflicts with the auto width in
  `2026-10-07-sidebar-layout.md` D5).
- Moves without a button pressed (`Moved`). No hover effects.

## Implementation

- `src/app/mouse.rs`: `App::mouse(&mut self, ev: MouseEvent, now: Instant)`,
  the click counter (`last_press: Option<(col, row, Instant, count)>`)
  and the drag state (`drag: Option<DragState>`). It dispatches to the
  existing actions (`Action`, `SidebarAction`, `VisualAction`,
  `PickerAction`, `HelpAction`), so mouse and keys share behaviour.
- `src/app/layout.rs` (or inside `mouse.rs`): the `Layout` struct and
  `App::hit`.
- `src/ui/mod.rs` and the pane draw functions record their rects and the
  list scroll offsets into the layout.
- `src/app/run.rs`: mouse capture enable and disable as in D1. Map
  `Event::Mouse`.
- `src/config.rs`, `config.default.toml`: `[mouse] enabled`.
- README: a "Mouse" bullet group (click, double-click, drag-to-copy,
  wheel, Shift+drag for native selection, `mouse.enabled = false`).
- Spec `2026-10-07-ramble.md`: mark R3 superseded by this spec.

## Testing

All tests drive `App` with synthetic `MouseEvent`s and `Instant`s after
one `ui::draw` into a `TestBackend`, so the layout is real.

- Click text: the cursor moves to the cell, with wide characters and
  clamping at the line end. Visual mode is cancelled.
- Click a files row: focus and selection. Click the arrow: expands.
  Double-click a file: it opens. Double-click outside 400 ms: no open.
- Click an outline row: selected. Double-click: the cursor jumps to the
  heading.
- Double-click a link: followed (history grows). Double-click a word:
  that word is yanked (recording clipboard). Triple click: the line is
  yanked.
- Drag: a selection from press to release, yanked on release, visual
  stays. A press and release without a drag yanks nothing. Dragging
  below the text area scrolls.
- Wheel over the content while the sidebar has focus: the content
  scrolls and focus stays. Wheel over the sidebar: the selection moves.
- Picker: click selects, double-click opens, the wheel moves. A click
  outside the picker or help popup closes it.
- `enabled = false`: `run` doesn't enable capture (unit-test the setup
  function's command list). Mouse events, if any, are ignored.
- A no-layout (`Layout::default()`) mouse event is a no-op.

## Out of scope

- Hover effects, right-click menus, border resizing, horizontal scroll,
  and mouse in the `:` command line.
