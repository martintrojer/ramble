# Key clue: next-key hints for pending sequences

Status: approved design (user answers Q1–Q6).

## Problem

ramble has many multi-key sequences: `g…`, `z…`, `[…`/`]…`, `C-w …`,
`m{a-z}`, `'{a-z}`, `y{motion}`, the leader with its sub-prefixes
(`<leader>z…`, launcher prefixes like `<leader>r…`), and launchers the
user configures. The only way to find what comes after a prefix is `g?`,
which shows the whole table. nvim's mini.clue answers the narrower
question at the moment it comes up: you've typed `<leader>`, so here is
what can follow.

## Behaviour

- **Hidden while idle.** With no pending keys, no clue is drawn.
- **Appears only on a pause.** After the first key of a sequence, if no
  further key arrives within 400 ms (a fixed constant), a box opens in the
  bottom-right corner. It lists each key that can come next and what it
  does. If the user types the whole sequence quickly, nothing is drawn.
- **Never takes focus.** It doesn't take keys. The next key goes to the
  keymap as usual:
  - if that key extends the sequence, the box updates at once, with no
    second delay;
  - if it completes or breaks the sequence, the box closes.

  Esc, `C-c` and an unknown key all close it, because they clear the
  pending keys.
- **One setting:** `[keys] clue = true` (the default). `false` turns it
  off. Its content is never configured. It comes from `help::BINDINGS`,
  the launchers in config, and the current state.

## Triggers

The clue is shown in exactly these states:

1. `App::pending` is non-empty: `g`, `z`, `Z`, `[`, `]`, `m`, `'`, `C-w`,
   `<leader>`, `<leader>z`, and any launcher prefix.
2. `Mode::OpPending`, after `y`.

A typed count by itself (`3`) does not show the clue. A count followed by
a prefix (`3g`) does, and the count is left out of the box title.

## Content

The rows come from the same source the `g?` popup uses:

1. Take the `BINDINGS` rows whose context applies right now (the
   `ctx_shown` rule: Normal or Visual with focus on the content, Sidebar
   with focus on a sidebar pane, Any for both) and that pass `avail`.
   Leader rows must also pass `leader_free`. Add the launcher rows. Rows
   that can't do anything are hidden (Q4), the same as in `g?`.
2. Expand each row's alternatives (`"gd, Enter, C-]"` → `gd`, `Enter`,
   `C-]`) and parse each one into key events with the parser the help
   tests use. Move that parser from `#[cfg(test)]` into normal code.
3. Keep the alternatives whose key sequence starts with the typed prefix
   and is longer than it.
4. Group what remains by the next key:
   - **One alternative ends at that key**: show the key and the row's
     description (`d  follow the link`).
   - **Several sequences continue past it**: show the key and `+label`.
     If every row under it belongs to one `Group`, the label is that
     group's title in lower case (`z  +pickers`). Otherwise it is
     `+N keys`.
   - **A placeholder** (`{a-z}`, `{motion}`) shows as a single row with
     that placeholder as its key (`{a-z}  set a mark`).
5. In `OpPending`, the rows are the operator's own keys: `y` (line), `f`,
   `F`, `u`, and one row `{motion}  yank over a motion`. They come from
   the `y…` rows in `BINDINGS`, the same as everything else.
6. Sort by key, with plain characters before named and control keys.
   Display keys the way `g?` does (`Space` for a space leader, `C-w`).

If nothing matches (for example, a launcher prefix whose launchers are
all unavailable), no box is drawn.

A test checks that every prefix the keymaps return `Pending` for produces
at least one clue row in some context. A new prefix without rows then
fails the build, in the same way that
`every_row_resolves_in_its_context_and_has_a_description` catches
rows that don't match a binding.

## Layout

- A bordered box anchored at the bottom-right of the area above the
  status line, inset 1 column from the right edge.
- The title is the typed keys, as `g?` shows them (`Space z`, `C-w`).
- Each column is `key  description`, padded to the widest key. The width
  fits the content, capped at the screen width minus 4.
- The height is at most half of the area above the status line. If there
  are more rows, they wrap into more columns, side by side, and the box
  grows wider. If they still don't fit at that width, the last visible row
  becomes `… N more`. Nothing scrolls.
- It is drawn on top of everything except the help popup and the picker.
  Those take their own keys, so no prefix is pending while they are open.

## Implementation

- `src/app/clue.rs`:
  - `ClueState { since: Option<Instant>, shown: bool }`.
  - `App::clue_rows(&self) -> Vec<ClueRow>`, a pure function of state.
  - `ClueRow { key: String, desc: String, group: bool }`.
- Timing: `handle_key` sets `since` to now when a sequence starts
  (pending goes from empty to non-empty, or OpPending is entered). It
  clears `since` and `shown` when the sequence ends. `App::tick(now)`, which
  `run` already calls on every 100 ms poll, sets `shown` once
  `now - since >= 400 ms`. `shown` stays set while the sequence grows, so
  the box updates with no second delay. The 100 ms poll means the box
  opens 400–500 ms after the key. That is fine.
- `src/ui/clue.rs`: the layout above, using `Clear` and a bordered block,
  drawn last in `ui::draw` before the help popup and picker.
- Config: `keys.clue: bool` (default true) in `config.rs`, the raw TOML
  struct, and `config.default.toml`.
- No new keys, so `BINDINGS` doesn't change. Add the `[keys] clue` line to
  the README config section and a sentence to the README "Around the
  edges" list.

## Testing

- **Rows.** App tests call `clue_rows()` after feeding keys, with no
  timing involved:
  - `g` lists `g` (top), `d` (follow), `v`, `x`, `R`, `?`, `r` (`+N`).
  - `<leader>` lists `z +pickers`, `e`, and launcher prefixes such as
    `r +…`.
  - `<leader>z` lists `f`, `s`, `z`, `b`, `l`, minus any unavailable without
    a server.
  - `C-w` lists `h`, `l`, `w`, `W`, `j`, `k`, `p`. With sidebar focus, it
    lists only the keys that apply there.
  - `m` gives the single row `{a-z}`.
  - `y` (OpPending) gives `y`, `f`, `F`, `u`, `{motion}`.
  - A count alone gives no rows and no box.
- **Timing.** Use `tick` with synthetic `Instant`s:
  - nothing at 399 ms, shown at 400 ms;
  - a second key after it is shown updates the box with no new delay;
  - a sequence completed under 400 ms never sets `shown`;
  - Esc clears it.
- **Coverage.** Every `Pending` prefix has rows (see Content).
- **Render** (TestBackend):
  - The box is at the bottom-right above the status line, with the title
    and rows.
  - Overflow on a short terminal wraps into columns or ends with
    `… N more`.
  - The box doesn't cover the status line.
- **Config.** `clue = false` never shows it.

## Out of scope

- Showing clues while idle, configuring the content, choosing where the
  box goes, configuring the delay (a fixed 400 ms by the user's choice),
  and clues inside the picker, help or command line.
