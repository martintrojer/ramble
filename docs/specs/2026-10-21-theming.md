# Theming, and a readable default config

Shared by ramble and debrief: the same file sits in both repos'
`docs/specs/`. Agreed with the user 2026-10-21.

## Problem

- Both apps hardcode Catppuccin Mocha. ramble's `[render] theme`
  accepts only `"catppuccin-mocha"`; debrief has no theme key.
- The palette is copied: `render::palette` (ramble), `ui::palette`
  (debrief), and ramble's UI repeats hex literals file by file
  (`content.rs`, `clue.rs`, `hover.rs`, `help.rs`, `hints.rs`,
  `status.rs`, `picker.rs`, `sidebar.rs`, `comment_box.rs`). debrief has
  `SELECTED` in `ui/commit.rs` and ANSI `Color::Cyan` / `Color::Yellow`
  in `ui/log.rs`.
- Users can't change one colour. The motivating case: Mocha with a
  higher-contrast cursor-row background.
- On a light terminal the text (`#cdd6f4`) is unreadable, since the main
  area is never painted.
- `config.default.toml` in both repos is hard to read: no section
  headers worth the name, `##` prose and `#` values mashed together.

## Design

### Config

Both apps get the same `[theme]` table:

```toml
[theme]
name = "catppuccin-mocha"   # a built-in, or a path to a base16/base24 YAML file
syntax = "Catppuccin Mocha" # code highlighting; unset: follows `name`
fill = false                # paint the theme background behind everything

[theme.colors]              # overrides, any subset
surface0 = "#45475a"
cursor_bg = "#585b70"
```

Every key is optional. With no `[theme]`, both apps look exactly as
today, apart from the two changes under *Visual changes*.

### Palette (16 colours) and roles

**Palette keys**, the colours a scheme provides:

| key | meaning | today's name |
|---|---|---|
| `bg` | main background; popups; ramble's `:` command prompt; dark text on coloured badges | BASE |
| `bg_dark` | status line; ramble's sidebar filter prompt; debrief's chip row over the log | MANTLE |
| `surface0` | subtle highlight | SURFACE |
| `surface1` | stronger highlight | (ramble `SELECTION_BG`) |
| `surface2` | strongest highlight | (debrief `SELECTED`) |
| `muted` | borders, hints, dim text | OVERLAY |
| `text` | text | TEXT |
| `red` `orange` `yellow` `green` `cyan` `sky` `blue` `purple` `pink` | accents | RED PEACH YELLOW GREEN TEAL SKY BLUE MAUVE PINK |

**Role keys**: one key per UI use, defaulting to a palette colour or a
blend of two. A role key overrides the default; otherwise the role is
derived from the *final* palette, after its own overrides.

| key | default | used by |
|---|---|---|
| `cursor_bg` | `surface0` | cursor row (ramble content, sidebar, picker; debrief log, diff, file list, commit list, picker), the open commit's row |
| `selection_bg` | ramble: `surface1`; debrief: `surface2` | visual selection and the rows of a comment being typed, in both apps |
| `add_bg` | blend(`green` over `bg`, 20%) | debrief added rows |
| `del_bg` | blend(`red` over `bg`, 20%) | debrief removed rows |
| `hunk_bg` | blend(`purple` over `bg`, 12%) | debrief hunk headers |

`blend(fg over bg, p)` = per channel `(fg*p + bg*(100-p)) / 100`, in
integer arithmetic, as debrief's `palette::blend` today.

Both apps accept every palette and role key. A key an app doesn't use
(debrief's `add_bg` in ramble) is accepted and ignored, so one
`[theme.colors]` block can be copied between the two configs. An unknown
key is an error, as elsewhere in the configs.

Values are `"#rrggbb"` or `"rrggbb"`, case-insensitive. A bad value is a
config error that names the key, with its line (ramble) or its key path
(debrief), in each app's existing error style.

`muted`). For the others, `surface0/1/2` and `muted` are blends of `text`
over `bg` at 12/20/28/45%, since their base16 slots aren't surfaces
(Solarized's base02 is a grey with text-level lightness, Nord's base04 is
a foreground).

### Scheme files

When `name` contains a `/` or ends in `.yaml` / `.yml`, it is a path: `~`
expands to `$HOME`, and a relative path is relative to the config file's
directory. The file is a
[tinted-theming](https://github.com/tinted-theming/schemes) base16 or
base24 scheme. Parse it with a small line parser, not a YAML crate:

- `baseXX: "<hex>"` or `baseXX: <hex>`, optionally indented (under
  `palette:`), `#` optional in the value, and a trailing `# comment`
  ignored. `XX` is `00`–`0F`, and `10`–`17` for base24.
- `variant: "dark"|"light"`, optional.
- Every other line is ignored. A missing `base00`–`base0F` is an error
  naming the slot and the file.

Mapping: `bg`=base00, `bg_dark`=base01, `text`=base05, `red`=base08,
`orange`=base09, `yellow`=base0A, `green`=base0B, `cyan`=base0C,
`blue`=base0D, `purple`=base0E. `sky`=base15 and `pink`=base17 when
present, else `cyan` and `purple`. `surface0/1/2` and `muted` are blends
of `text` over `bg` at 12/20/28/45%. The `syntax` default for a file is
Catppuccin Mocha for a dark variant (or no variant line) and Catppuccin
Latte for a light one.

### Syntax highlighting

`syntax` takes a two-face embedded theme name (two-face 0.5
`EmbeddedThemeName`, its `as_name()` string), matched case-insensitively:
`Catppuccin Mocha`, `Solarized (dark)`, `gruvbox-dark`, `Nord`,
`Dracula`, `OneHalfDark`, and so on. Unknown: an error that lists the
valid names. Unset: the built-in's `syntax` from the table above. This
replaces the fixed `CatppuccinMocha` in ramble's `render::code_theme`
and debrief's `app/highlight::code_theme`.

### `fill`

`fill = true` paints `bg` under every cell the app draws (the main area,
the sidebar, the diff) before drawing it, and draws text in `text`. Areas a
widget clears first (the sidebar) are filled after the clear. A
light scheme on a dark terminal, or the reverse, then reads correctly.
`false` (the default) leaves the terminal's own background as today.

### ramble's `[render] theme`

It stays accepted, for configs that already set it, but leaves the
default config's value lines: the `[render]` prose there says it is
deprecated in favour of `[theme] name`, without a `# theme = ` line, so
the uncommented default file still loads with no warnings. `"catppuccin-mocha"`
works as before and adds a warning to `Config.warnings`:
`[render] theme is deprecated; use [theme] name`. Any other value is the
same error as `[theme] name`'s. When both are set, `[theme] name` wins.

### Visual changes at the default theme

Everything stays the same colour, except:

- debrief's log markers: `●` new goes from ANSI cyan to `cyan`
  (`#94e2d5`), and `◐` updated from ANSI yellow to `yellow` (`#f9e2af`).
- None other. A test pins each role's Mocha value to today's constant.

### The code shape

- One module per app: ramble `src/theme.rs`, debrief
  `crates/debrief/src/theme.rs`, with the same public names:
  - `pub struct Palette { pub bg: Color, ... }` with the 16 palette keys
    and the 5 role keys as fields. Each app carries all of them.
  - `pub const MOCHA: Palette`, the default.
  - `pub fn builtin(name) -> Option<Palette>` and `pub const BUILTINS:
    &[&str]`.
  - `pub fn blend(fg, bg, pct) -> Color`.
  - The scheme-file parser.
  - `pub struct Theme { pub palette: Palette, pub syntax:
    syntect::highlighting::Theme, pub fill: bool }`, built from the
    config.
- `Config` keeps `[theme]` unresolved: every key optional, and an
  explicit key stays set even when it equals the Mocha value, so a role
  override still wins after a palette change. The uncommented default
  file therefore equals `Config::default()` in every other field and
  resolves to the same theme; the default-file test checks those two
  things, not whole-`Config` equality. `theme` is a public module
  (`pub mod theme`).
- The config module parses `[theme]` into an unresolved form. Resolution
  (built-in or file, then overrides, then derived roles, then syntax)
  happens once at start, and its error goes through the existing config
  error path.
- The `const` palettes go: `render::palette` (ramble), `ui::palette`
  (debrief), and every hardcoded `Color::Rgb` / ANSI colour in UI and
  render code. Draw code reads the palette from the app
  (`app.theme().palette.blue`). In ramble, render code reads it through
  the existing `render::Theme` argument, which absorbs the palette and
  the syntax theme next to `math`.
- debrief highlights on worker threads (`spawn_show`, `spawn_working`,
  `highlight_later` in `app/commit.rs`): each gets the syntax theme by
  `Arc`, not a global.
- Tests that compared against `palette::X` compare against `MOCHA.x`.

Two copies of `theme.rs` are accepted for now (the two repos release
separately). The tables and names must match: each repo has a test that
pins `MOCHA` and one other built-in to the values above.

### The default config, rewritten

Both `config.default.toml` files get this layout:

```toml
# ramble configuration
#
# Every option is listed with its default value, commented out.
# To change one, remove the "# " in front of it and of its [section].


# ── Rendering ────────────────────────────────────────────────────────────

# [render]

# Upper bound on the reflow width, in columns.
# max_width = 100

# Draw LaTeX math ($…$, $$…$$, ```math) as Unicode; false shows the source.
# math = true


# ── Theme ────────────────────────────────────────────────────────────────

# [theme]
...
```

Rules:

- Prose and values both use a single `#`. No line starts with `##`
  (a literal such as the export's `"## Item N [ISSUE]"` inside prose
  is fine).
- A **value line** is `# <key> = <value>`, `# [table]` or
  `# [[table]]`. A value that opens `[` or `{` without closing it on its
  line continues through the line that closes it (`# kinds = [` …
  `# ]`). Uncommenting means removing `# ` from value lines only.
- A **prose line** never matches the value-line shape. An example inside
  prose is indented two extra spaces after `# ` and introduced by
  `For example:`, so it isn't a value line:
  `#   command = ["sh", "-c", "…"]`.
- Each section opens with a banner: two blank lines, then
  `# ── <Title> ` padded with `─` to exactly 78 columns, then a blank
  line, then the `# [table]` line, then a blank line. A section with no
  single table (`[[launch]]` entries, or only prose examples such as
  `[[lsp.server]]`) has no `# [table]` line: its prose follows the banner,
  then any `# [[table]]` value blocks.
- Within a section, each key is its prose, then its value line, then one
  blank line. Prose wraps at 76 columns.
- The file opens with the header block shown above (the app's name in
  its first line).
- The content (every key, its default, what its prose says) stays the
  same, apart from the new `[theme]` section and ramble's deprecated
  `[render] theme`, which becomes prose (see *ramble's `[render] theme`*). Only layout and wording
  change. Wording may be tightened, but every fact stays, except the
  old opening's `Lines starting with "##" are explanations`, which the
  new header block replaces.

The tests that read the file move to the new rules: ramble
`uncommented_default_file_equals_defaults` and
`commented_default_file_loads_as_defaults`; debrief
`commented_default_file_is_the_defaults`,
`uncommented_default_file_is_the_defaults`, `documented` and
`default_keys`. A new test checks the banner rule: every `# ── ` line is
78 columns, preceded by two blank lines and followed by one.

### The `[theme]` section in the default config

It lists `name`, `syntax`, `fill`, a commented `# [theme.colors]` with
every palette key at its Mocha value, and the role keys the app uses.
Derived roles are shown with their Mocha values and a note that they
follow the palette when unset. The prose names the built-ins and the file
form, and says that an override replaces one colour of whatever `name`
selected. The user's example goes in as prose:

```text
# For example, Mocha with a stronger cursor row:
#   [theme.colors]
#   cursor_bg = "#585b70"
```

### Docs

- ramble `docs/guide.md` and debrief `docs/guide.md` (its `## Config`
  section) get a short *Theme* paragraph: built-ins, files, overrides,
  `fill`, and a pointer to this spec.
- README config bullets are unchanged.

## Out of scope

- Detecting the terminal background (OSC 11) and an `auto` theme.
- A shared crate for `theme.rs`.
- Switching themes at runtime.
- Nord, Dracula, Tokyo Night and others as built-ins: the file form
  covers them.
